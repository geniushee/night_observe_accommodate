## ADR 001: 지도 엔진으로 네이버 지도 자바스크립트 API v3 채택
* **날짜:** 2026-11-17
* **결정:** 대한민국 지역에 특화된 지도 렌더링 및 숙박 정보 검색과의 시너지를 위해 **NAVER Maps JavaScript API v3**를 채택한다.
* **배경 및 근거:**
  1. 국내 지형, 도로명, 행정구역 표기 및 POI 정보가 국내 사용자에게 가장 친숙하고 상세함.
  2. `naver.maps.GroundOverlay`를 지원하여 대용량 광공해 이미지 래스터를 위경도 바운딩 박스에 부드럽게 얹을 수 있음.
  3. 향후 네이버 플레이스 및 네이버 예약 연동 시 링크 호환성이 높음.
  4. 네이버 클라우드 플랫폼(NCP) 공식 v3 규격에 따라 `ncpKeyId` 인증 파라미터와 비동기 `callback` 방식을 적용하여 안정적인 지도 초기화 보장.

## ADR 002: 광공해 이미지 정밀 투영 변환(Warping) 및 에셋 최적화
* **날짜:** 2026-11-17
* **결정:** 원본 대용량 `Asia2025B.png`(14400x8400)를 웹 브라우저에서 바로 로드하지 않고, 한반도 영역(위도 32.8°~43.2°, 경도 124.0°~132.2°)을 추출하여 Web Mercator(EPSG:3857)로 사전 워핑 및 알파 채널을 적용한 최적화 PNG(`public/assets/asia2025_korea.png`)로 서빙한다.
* **근거:**
  1. 원본 전체 이미지는 수십 MB의 메모리를 점유하므로 모바일 환경에서 성능 저하 및 크래시 위험이 있음.
  2. 사전에 가공된 경량 PNG(약 150KB 내외)를 사용함으로써 모바일에서도 즉각적인 로딩과 부드러운 지도 줌/팬 성능을 보장함.
  3. 완전 어두운 자연 밤하늘(Black)은 `Alpha=0`으로 투명화하여 네이버 지도 고유의 위성 및 일반 지도가 돋보이도록 처리함.

## ADR 003: 숙박 데이터 수집 및 예약 링크 연동 방식
* **날짜:** 2026-11-17
* **결정:** 한국관광공사 TourAPI 4.0(숙박 정보)을 1차 소스로 활용하되, 개발 초기 및 API 키 부재 시에도 안정적인 구동을 위해 100개의 청정 지역 숙박 Mock 데이터를 내장하는 하이브리드 구조를 채택한다.
* **예약 링크 연동:**
  * 특정 플랫폼에 종속되지 않고, 네이버 예약/플레이스, 야놀자/여기어때 검색 쿼리 파라미터 링크, 숙소 공식 전화번호(`tel:`)를 제공하여 사용자 편의성을 극대화함.

## ADR 004: 모바일 사진 EXIF 메타데이터 추출 라이브러리 선정 (`exifr`)
* **날짜:** 2026-11-17
* **결정:** 스마트폰으로 촬영한 밤하늘 사진에서 GPS 위치(위도/경도) 및 촬영 시간을 파싱하기 위해 경량 고성능 라이브러리인 **`exifr`**를 선정한다.
* **근거:**
  1. 구형 `exif-js`에 비해 Web Worker 지원 및 성능이 우수하며 현대적인 번들러(Vite, ESM)와의 호환성이 뛰어남.
  2. HEIC(아이폰 기본 포맷), JPEG, TIFF 등 모바일 카메라로 촬영되는 다양한 포맷의 메타데이터를 안정적으로 파싱할 수 있음.

## ADR 005: 관측일지 데이터 영속성 및 백엔드 확장 전략
* **날짜:** 2026-11-17
* **결정:** 초기 단계에서는 사용자 개인의 관측일지 및 사진 데이터를 브라우저 로컬 스토리지(LocalStorage / IndexedDB)에 임시 저장하여 빠르게 기능을 검증하며, 별도의 회원가입이나 중앙 백엔드 서버 연동은 차후 단계에서 구현한다.
* **근거:**
  1. **초기 복잡도 최소화 및 빠른 검증:** 인증 및 서버 인프라 구축 없이도 핵심 기능(지도, 오버레이, 사진 위치 기반 일지 작성)의 UX를 즉시 완성하고 검증 가능.
  2. **오프라인/음영 지역 사용성:** 관측 장소 특성상 통신이 불안정한 산간 오지에서도 네트워크 연결 유무와 무관하게 로컬에 안정적으로 기록 가능.
  3. **점진적 확장성:** 차후 클라우드 동기화, 사용자 간 일지/사진 공유 커뮤니티가 필요해질 때 백엔드 API 및 인증 시스템을 단계적으로 도입.

## ADR 006: 주소코드 기반 공간 필터링 및 인접 지역 그래프(Graph) 비채택
* **날짜:** 2026-11-17
* **결정:** 화면 중심에서 가장 가까운 10개 숙소를 선별할 때 복잡한 인접 행정구역 그래프(Adjacency Graph)를 구축하지 않고, **시군구 중심점(Centroid) 기반 1차 후보군 선별 $\rightarrow$ 정밀 구면거리(Haversine) 계산 2단계 파이프라인**을 채택한다.
* **근거:**
  1. **실제 지리 거리와 행정구역의 괴리:** 지리학적으로 행정구역 경계는 인위적이므로, 인접 그래프를 구축하면 접경 지역(예: 평창-홍천 경계, 영월-단양 경계) 탐색의 복잡도만 증가하고 실제 최단 거리 숙소를 놓칠 위험이 있음.
  2. **극단적인 성능 우수성:** 100개~수천 개 수준의 공간 데이터는 브라우저 메모리상에서 단순 좌표 계산에 0.05ms도 소요되지 않으므로 그래프 탐색(BFS/DFS) 오버헤드보다 Centroid 필터링이 수십 배 가볍고 정확함.
  3. **네이버 지도 이벤트 결합성:** 지도 `idle` 이벤트 시 뷰포트 중심점을 기반으로 즉각적이고 부드러운 마커 갱신을 보장함.
